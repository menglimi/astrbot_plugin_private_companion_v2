# 基于 V2 框架的 V1 优化实现路径

**目的**：把 V1 里"用户看得见、看得懂、摸得着"的部分，**用 V2 的机制重做**（一条链：准入→生成→分段→投递+回执；`owner_key` 隔离；带指纹迁移；配置注册表），而不是把 V1 的补丁搬过来。

**排序原则**：体验优先于 parity。当前最差的是"看不见"（失败无原因、沉默无记录、主动无回看），所以 Phase 0 先做可观测性地基；V1 那 316 项"有意不迁/设计差异"不在本路径内，除非点名。

**验收纪律**：每阶段在**树静默**时验收（并行会话会让结论翻转）；开发期只跑定向套件，不构建、不跑全量。

---

## Phase 0 — 可观测性地基（先做，1–2 天）

| 项 | 现状 | 目标 | 落点 |
|---|---|---|---|
| 失败原因可回看 | `last_failure` 只在内存（`astrbot_host/multi_controller.py:63`），`refresh_settings()` 成功即清空 | 持久化最近 N 条失败（时间/码/原始原因），页面可回看 | runtime_metadata 或新表 `host_failures`；`_failure()`（`:339`）保留原始 code 不再泛化 |
| 错误码有中文 | 探测/启动链 **24 个码无标签**，页面退到"宿主最近一次操作未完成…" | 全部有中文 + 建议动作 | `pages/陪伴小屋/workspaces/host/app.js` 的 labels 表 |
| "为什么没回"可见 | 只有"入站未回复"式噪音（已修极性）；9 项契约未实现 | 先落三类：`silence` / `generation_failed` / `delivery_unknown` + 每轮汇总行 | 新配置组 `diagnostics.reply_log`（`enabled`/`level`/`preview_chars`/`include_content`）+ `config-editor.js` 同步声明 |
| 未知结果给人话 | 模型结果未知时整轮静默（如 `model_usage_unknown`） | 对话内一句简短提示（可开关），日志保留原因码 | `model_gateway` → `conversation/flow` |
| 主动链有读数 | 资讯链有 `diagnostic/probe`，但"候选长期为零""自关联冷却中"无读数 | 补这两个读数（复用现有 diagnostic 字段） | `proactive/news_events.py` + 感知/维护页 |

**验收**：启动失败时页面直接说原因；"为什么没回"一行可见；日志里不再出现"不是我管的"噪音。

## Phase 1 — 把 V1 的审计链变成 V2 的可视记录（2–3 天）

V1 的对标物是 `proactive_audit_log`（status/reason/motive/route/scheduled_ts/candidate_id/text_preview，带签名去重与截断）、表情运行时计数器、注入清单 `plan.manifest()`。V2 已有等价数据（候选/排程/投递表 + `delivery` 三态），缺的是**读出来给人看**。

1. 主动决策记录页：最近 N 条「为什么发 / 为什么不发 / 被什么压制 / 结果三态」，数据源复用现有表，**不新造存储**；
2. 日志侧同步落 `stage=reason` 与 `stage=delivery`（字段复用 `candidate_reason`/`render_state`/`failure_code`，与 `reply_management.py:64-73` 命名一致）；
3. 注入与事实注入的"每轮一行"（第 1、6 项），默认只记条数与字符数，正文走双闸。

**验收**：任意一次主动触达，能在页面上回看到原因、压制与三态；一次普通回合能在日志里看到"注入了什么"的摘要。

## Phase 2 — 用户级控制面：699 字段的收口（2–3 天）

现状：**49 组 / 699 字段**，全在配置编辑器里平铺，找不到东西。V1 的优势恰恰是"一句话说明 + 就近开关"。

1. 分层：常用 15–20 项进首屏（按域分组：回复/主动/记忆/媒体/作息），其余进高级区；
2. 每个开关补"开了会怎样 / 关了会怎样"的人话（V1 note 的写法，不是字段名直译）；
3. 关键开关旁给"为什么现在没生效"的就地解释（直接复用日志原因码）。

**验收**：想改的 20 项在首屏可达；每个开关有一句后果说明；被门槛挡住时，页面就地说明是哪道门槛。

## Phase 3 — 用户可见的 V1 功能补齐（按选定项，3–5 天）

从台账"真实欠账 29 项"里挑**用户可见**的（其余不动）：

| 项 | 缺口 | 落点 |
|---|---|---|
| Token 用量与费用视图 | V1 有，V2 只有软限额配置 | 聚合 `model_call_accounts`/`model_call_failures`（已知/未知/估算三态，**不编造费用**）→ 模型与连接页或治理页 |
| 独立排障面板 | V1 有；V2 诊断域有代码、**页面无入口** | 把 `diagnostics/service.py` 5 项检查 + 存储基线读数接到维护页 |
| 主用户语音档 4 项 | 语音链完成度最高，但缺主用户专属档（概率/关键词/提示词） | `conversation.voice_reply` / `expression` 补字段，复用现有语音链 |
| 被戳细档 7 项 | 缺超级反戳、连戳次数/间隔、被戳提示词、不调模型概率 | `conversation.pokes` + 主动戳已有基础 |
| 群聊高强度降载 7 项 | **V2 完全无替代**（唤醒窗口/阈值/冷却/合并窗口） | 并入 `conversation.group_participation` 或新域 |
| 群话题线 + 黑话联网参考 4 项 | 群话题线已在 V2 落地为有界摘要与配置；黑话联网释义仍未接入，当前只用群内证据 | **仅联网释义待产品决策** |
| T50 跨群转述与 @ 群友 9 项 | 被 T27 阻塞 | 排后 |

**验收**：每项落地都要有"页面上能看到 + 配置能改 + 一条断言"，不接受只有后端字段。

## Phase 4 — 迁移与收口（需要你明确发起）

`AGENTS.md` 已允许"收到明确迁移请求时，通过正式迁移流程读 V1 写 V2"，仍然**不改 V1 数据**。

1. 配置转换器补齐（现在**只有天气一组**）：按 `V1_V2_CONFIG_RESOLVED` 的落点逐组写转换器 + 迁移测试；
2. 页面上的"从 V1 导入"向导：读取 → 预览 → **逐组确认** → 写入 → 回执（带 dry-run）；
3. 身份对齐校验前置：迁移时强制比对 `platform/participant/bot_id/account_id` 与 `persona → role` 映射（这次 `bot_id` 事故就是这类问题的实例）；
4. 明确**不迁**清单（316 项设计差异）写进向导，避免误解为"漏做"。

**验收**：逐组可预览与回执；V1 数据只读不变；迁移后可回滚（快照 + 校验）。

## 依赖与风险

- **Phase 0 是其他阶段的前提**：不改可观测性，Phase 1/2 的"为什么没生效"没有数据来源；
- **树静默**：验收必须在无并行写入的窗口做，否则结论会被翻转（复测窗口里 21 分钟 21 个文件变动、2 块结论翻转就是实例）；
- **磁盘**：C: 只剩约 4.5 GB，出现过 `database or disk is full` 伪失败——全量验收前先清盘；
- **闸门**：当前还差约 71 项（其中 61 项纯测试改写，0 项确认动产品），Phase 0 可与闸门修复并行，但冻结验收要等闸门到 0。
