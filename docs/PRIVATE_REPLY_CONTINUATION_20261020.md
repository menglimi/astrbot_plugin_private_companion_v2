# 私聊回复的时序与承接（2026-10-20）

## 问题与证据

“来张自拍看看”之后，用户的“看看”和“当然”都在接同一次初始回复，不能因插件为每条输入建立了独立处理事件，就把它们理解成不同的话题。

本机日志与用户提供的记录可以相互对应：22:51:21 收到“看看”时，第一轮仍在发送分段；22:51:43 收到“当然”时，第二轮尚未发送。第二轮在 22:51:50 才进入发送阶段，随后出现“与其看照片，投影过来”的内容；第三轮到 22:52:16 才进入模型请求。模型按串行处理后的完整历史理解“当然”，容易把它误当成对较晚投影邀请的确认。

同时发现背景构建读取的是 `native_input.received_at`，但原生快照的字段实际是 `at`，因此退回了准备时刻。这个偏移会把输入到达后才发出的主动消息或提醒误纳入输入之前的背景。

当时首选对话 Provider 另有 403 并切换了回退 Provider。它是日志证实的独立配置问题，不足以单独解释指代错误，本次未改动模型账号配置。

## 处理

- `conversation/private_reply_context.py` 只读当前已授权私聊的原生输入与发送返回记录。以原输入的 `at` 为界，分别保留 `before_input` 和 `after_input`；后者只包含已发出的角色消息，不将之后到达的用户输入提前当成本轮指令。
- 时间线携带原 `turn_id`，供模型把同一次回复的多个气泡合并理解。最近发送轮次仅是时间锚点，不由程序强制指定用户在回复哪一句；引用、否定、纠正和转向仍由模型结合语义判断。
- 稳定提示说明：较早的确认不能指向后来才发出的邀请或问题；同一较早回复可承接多个连续确认，短话保留原任务对象与进度。之后的已发内容只用于了解进展、避免重复执行。
- 时间线在实际模型请求时通过既有临时 user 上下文刷新，保留等待期间的发送进展；不写入持久对话，不修改共享宿主历史，也不把动态时刻和正文加进 system 前缀。
- 连续输入防抖保留各条原话的独立到达时间，整组合并消息以首条输入作为保守时界。已发送背景和互动间隔改为读取原生快照的 `at`。

这属于回复上下文的正确性修复，没有新增配置开关或页面控件。原有分段、发送、额度、身份授权及未知结果不重放继续按原流程执行；没有用关键词强制认定“当然”一律是同意，也没有丢弃输入或强制取消正在发送的回复。

## 验证

定向回归使用隔离宿主和本地替身，复现同一初始回复发送期间的两次跟进，以及排队期间第二轮后来才发送的内容；核对未发送草稿排除、当前用户输入不重复注入、其他窗口和失效授权隔离、临时上下文不入库、稳定 system 前缀及合并输入时序。交付包的测试结果另存于包外验收记录。真实模型如何选择措辞与承接仍需重载后的实际会话观察。
