# V2 来源、经历与混合查询的增量召回

本切片接续[事实索引性能与锁竞争](CORE_MEMORY_SEARCH_PERFORMANCE_20260924.md)。`memory.query` 的 `sources / experiences / all` 及显式向量查询已改为增量投影、有限候选续页和命中后正本复核，不再每次读取全部历史对象、逐个鉴权并在 Python 中重建完整排序。默认词法事实查询继续使用已经验收的 `FactIndex / FactQuery`。

代码已落入 V2 主树。主库 schema 升至 **v26**，可丢弃搜索缓存布局升至 **format 2**。本轮只打开临时合成库，没有在线重载、真实模型或 QQ 调用、鼠标操作，也没有访问 V1 用户数据。

## 查询怎样工作

1. 查询入口按当前身份、原角色、私聊受众及会话预算校验访问资格。
2. 从主库变更流读取新增或变化的对象编号。索引已同步时只核对末尾序号、随机见证令牌与缓存版本；不争取缓存写锁。
3. 未同步时，每次最多推进 256 个变更对象/原文片段；每个来源片段最多 2000 字，步长 1900 字。对象很多或单条原文很长时，检查点保存已经处理的位置，下一页或下一轮继续。
4. 词法查询在数据库中排序并分页，单次最多取 128 个候选来复核。返回正文来自当前正本；缓存的标题、主体、标签和正文不能授权读取，也不能代替正本。
5. 还没建完索引时返回空 `items`、`index_state=catching_up`、`complete=false` 和续页游标。没有把最近 N 条记录当作完整历史，也没有先返回一个前缀排名冒充最终结果。

索引变更与进度在同一缓存事务中提交。缓存写入失败会同时回滚词项和检查点，不扣除成功查询预算；缓存忙时返回原有 `memory_index_busy`，调用方稍后重试。

### 对象与归属

| 对象 | 变更依据 | 命中后的读取 |
| --- | --- | --- |
| 人类消息 | `conversation_inputs` | 原事件、私聊归属和当前来源授权 |
| 已确认发送的 Bot 回复 | `conversation_sent_history` | 原投递回执、正文、依赖及当前来源授权 |
| 经历摘要 | `memory_views` | 当前经历版本，以及每条陈述的来源/事实版本 |
| 混合查询中的事实 | `memory_atoms` | 原 writer、当前版本、命名空间、保留方式和有效时间 |

分区继续以 installation、逻辑 Bot、V2 role 和人类主体区分；不同查询种类及事实命名空间分别建投影。中文 Bot/role 标识与 SQLite 事务中的归属键完全一致。人格映射到同一个 V2 role 的共享语义未改变。

Bot 回复先对已经确认发送的文字脱敏建词项，真正命中时才由原所有者发布引用。未命中的历史回复不会全部物化成记忆来源。缓存片段 ID 由原事件、精确 SourceRef、片段位置、内容及发言者确定；实际交给模型的证据和句柄仍使用发布后的真实治理哈希，兼容脱敏来源的 HMAC 哈希。

### 续页与覆盖说明

- 游标限定原查询参数、索引代次、变更锚点、语料 epoch、排序时间和偏移；其他分区变更影响全局 BM25 时，也会使旧排名游标失效。
- 撤回、更正、遗忘和当前权限变化均需重新复核。候选失效也推进位置，避免一批失效记录永远挡住后面的有效对象。
- 查询调用次数、字符预算与会话期限照常计算。新会话可以接续持久索引构建进度，不能通过换游标重置当前会话预算。
- 建索引前已经撤销或缺失的原文不会写入词项，同时保留 `unavailable_sources` 缺口标记。该标记跨页、跨重启保存，重建缓存时重新评估；不会为清掉标记而在每次查询中重读全部来源。
- `complete` 表达本次投影候选的查询进度及已知来源缺口，不证明现实中某事没有发生；返回值继续提供 `no_match_is_not_proof_of_no_event`。未采集材料、被忘记的材料及当前不可见历史不等于全量现实记录。

`MemoryExperiences.list()` 同步改为按主键续页，每次最多检查 128 个候选，SQL 预筛选实体后仍核对当前正本。即使整页来源失效，也会返回可继续的位置和明确覆盖状态。

## 显式向量与混合排序

向量仍由调用方显式提供，要求明确模型/版本、有限非零向量以及匹配的文档哈希和维度，不隐式调用模型或生成 embedding。

精确余弦计算每次最多处理 256 条向量，分数和进度写入派生缓存。全部计算完成后才做 SQL 排名、词法/向量 RRF 融合与结果分页；过程中返回 `index_state=ranking`。没有在相似度排序前截取最近记录。

计算任务只绑定当前分区、索引版本、模型及查询向量。同一个版本的余弦计算可以跨轮、跨查询服务重建复用，避免超过单轮预算后永远从头计算。查询时间、主体、命名空间、权限以及最终排名依旧按当前查询过滤：先过滤，再生成向量名次并融合。查询结果游标仍属于各自原会话，不跨会话复用。

`vector_coverage.embedded / eligible` 按当前过滤条件统计；`complete` 只表示向量计算进度完成，不表示每个对象都已经提供了向量。过期计算任务在后续计算写入时清理；遗忘和清空索引会同时清除文档、向量、计算任务及分数。旧 format 1 中已有的词法/向量表保留供原低层接口使用；它们不会凭空变成新分区的有效 embedding，新投影需要匹配自身 ID 与哈希的向量。

## 主库 v26 与恢复

新增 `memory_recall_changes(sequence, owner, kind, object_id, token)`，只记录对象编号与随机见证令牌，不复制消息正文。四类对象的 INSERT、真实 UPDATE 和 DELETE 通过 12 个触发器在原事务内记变更；普通更新记新值，归属变化才额外记旧归属。没有变化的重复 UPDATE 不产生新投影或无意义地清除向量。

升级一次性为已有对象补编号，并新增按归属/类型/序号查流的索引及遗忘证据索引。主库数据、DDL、版本号和迁移回执原子提交；失败可以重试。重开会核验迁移指纹及触发器定义，缺失或被替换的变更追踪不会当作完整索引继续使用。

派生缓存可能早于外层主库事务提交。若外层回滚后变更序号被再次使用，随机见证令牌能够区分两次不同的历史，触发重建，避免将回滚数据错当作已同步正本。半批投影失败、缓存锁冲突、重启续建和同时删除词项/向量均有定向验证。

## 本机合成数据测量

使用公开 accept/save 入口建立 **1001 条来源、1000 条经历**；目标放在最早记录。旧版与新版读取同一临时主库，各自使用独立空缓存。基线动态加载本轮修改前的 `query.py`，公用 writer、来源治理与底层运行环境保持相同。每类查询测量 4 次，热查询取后 3 次中位数。

| 热查询 | 原完整读取路径 | 新增量路径 | 原路径批量取数 | 新路径批量取数 |
| --- | ---: | ---: | ---: | ---: |
| 来源 sources | 904.08 ms | 7.80 ms | 1001 行 | 0 行 |
| 经历 experiences | 1399.92 ms | 6.56 ms | 1000 行 | 0 行 |
| 混合 all | 2281.59 ms | 11.99 ms | 2001 行 | 0 行 |

“批量取数”统计从对象表和变更流批量带入 Python 的行数，**不是 SQLite 内部扫描页数**。新路径仍会读取命中正本及依赖：来源查询每次 3 次来源读取，经历查询每次 1 次经历及 2 次来源读取，混合查询每次 1 次经历及 5 次来源读取。

新路径全部冷建投影分别为 236.22、159.60、436.09 ms，共 4、4、8 批；单批最大为 67.13、42.25、61.58 ms。冷建指标直接计量索引推进，不包括完整会话查询开销；基线第一轮同时包含查询和全量物化，不能直接当作相同口径的冷建对比。

这些数字仅反映本机短文本、稀疏命中的合成场景。不是线上延迟保证，也不是一万条经历或真实提供商向量的性能验收。

## 仍需独立处理的开销

- 后台 `MemoryReflection.prepare()` 仍调用旧 `_documents(..., "sources")`，并读取既有整理清单和事实。公共查询已经切换，后台反思选材尚未增量化，需要单独的持久选材进度，不能直接截取前 N 条。
- SQL FTS 排序、精确向量融合、覆盖计数、深层 OFFSET，以及列表的 JSON 实体筛选仍可能随匹配量增长。本轮限制 Python 物化与原件复核数量，没有设置 SQL 时间硬上限，也没有 ANN 索引。
- 单个极长原文或经历文档仍需读取/解码整个对象；片段数有界不等于每次磁盘字节数或依赖递归成本都有硬上限。
- v26 初次升级需同步扫描现有对象一次来补变更指针。主库锁等待、同步初始化和大批变更仍保留原机制；变更流的长期压缩及后台索引预热尚未实现。
- 真实大库、密集命中、外部 embedding 提供商和在线多目标压力测试尚无本轮现场证据。
