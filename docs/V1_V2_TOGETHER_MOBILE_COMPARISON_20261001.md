# V1 / V2 一起房间手机链路对比

更新时间：2026-10-01

本文比较当前 V1 手机网关路径与 V2 原生 Together 接线，重点是「在一起拓展」和「现实触及拓展」合并到同一个手机入口后的行为。比较依据是当前源码、提供方合同测试和 Reality 网关测试，不把设计稿或旧交付包当成当前实现。

## 1. 结论摘要

V1 的手机房间链路以 Together 一次性房间票据和 `resume` 恢复为中心：网关准备房间服务、发票据、把链接交给手机。V2 在同一个 Reality 网关上先解析手机会话对应的 V2 私聊目标，再逐动作复核当前 Bot、角色、主体和授权；V2 建房、邀请、加入都写入 Together 原生操作账本。

V2 的邀请不会复制房主身份或创建第二个房间。`together.room.join` 会把受邀成员挂到已存在的 `RoomSession`，并给该成员签发一次性短期连接 URL。没有匹配 V2 目标时才保留 V1 建房兼容路径；匹配到了 V2 但没有权限时直接拒绝，避免绕过 V2 授权。

## 2. 功能对照

| 能力 | V1 手机路径 | V2 手机路径 | 当前优化结论 |
| --- | --- | --- | --- |
| 入口 | Reality 移动网关，调用 Together 旧房间接口 | 同一 Reality 移动网关，调用 V2 原生桥接，再由 Together 提供方执行 | 手机端不需要第二套入口 |
| 认证 | 配对令牌换移动会话；后续请求用会话令牌 | 相同的 Reality 会话认证，V2 再通过 Reality 证明会话对应的用户 | 会话认证和 V2 身份认证分层 |
| 配对 | `POST /pair`，绑定 `allowed_user_id` | 同一 `/pair`；V2 按会话用户查找私聊目标 | 不新增重复配对协议 |
| 状态 | `/status` 返回 Reality、位置、设备和 Together 可用性 | `/status` 额外返回 V2 `matched`、`ready`、模式和逐动作 capability | 手机可以在提交动作前知道当前授权状态 |
| 建房 | 网关准备 Together 后直接签发旧 `ticket_token` 链接 | `together.room.create` 经过 V2 scope/persona/权限复核后签发；手机只收到经网关改写的 URL | V2 优先，未匹配时兼容 V1 |
| 模式 | `call`、`watch`，以及由旧房间服务决定的其他模式 | 仍由 Together manifest 返回 `call`、`watch`、`work`、`novel` 等实际模式 | 能力目录是单一事实来源 |
| 邀请 | 旧手机建房接口没有与 V2 身份绑定的邀请主链；旧房间可有内部邀请/恢复票据 | `POST /room/invite` 调 `together.room.invite`，默认 600 秒、允许 60–3600 秒 | 邀请成为可审计的 V2 操作 |
| 加入 | 主要是携带票据打开房间，身份与 `resume` 宽限机制耦合 | `POST /room/join` 先用受邀者自己的 V2 身份接纳，再返回成员连接 URL | 加入者不会继承房主身份 |
| 同房连接 | 旧票据打开或恢复一个房间连接 | 成员连接挂到已有 `RoomSession`，成员广播、断线恢复和关闭按成员处理 | 解决“邀请成功但未真正入房”缺口 |
| 成员隔离 | 旧路径主要依赖房间票据和 websocket resume | 摄像头帧按成员隔离；文本保留说话人标签；每个成员有自己的恢复令牌 | 降低跨成员泄露和串上下文风险 |
| 能力授权 | Together 旧房间服务和网关开关决定是否可用 | V2 对 `create`、`invite`、`join` 逐动作复核，Reality 设备能力仍按各自 grant 和提供方规则复核 | 一起房间权限不扩散为设备权限 |
| 角色与人格 | 由旧 Together 配置和房间票据带入当前执行环境 | V2 从已认证会话解析主体、角色绑定、Bot/账号和执行配置；提供方再次校验 persona 与 scope 一致 | 手机不提交或伪造人格提示词 |
| 模型与语音 | 使用 Together 当前模型、TTS/STT 和房间设置 | 仍由 Together 执行，V2 只传递已复核的 host execution；工作协同还要求 Screen 能力 | 保持提供方归属，避免重复实现媒体服务 |
| 幂等 | 旧接口没有统一的移动业务 `request_id` 合同 | 建房、邀请、加入均要求稳定 `request_id`；同 ID 同参数复用原操作 | 网络重试不会重复建房或重复入员 |
| 未知结果 | 旧客户端容易重新发一个新票据，无法区分“未发出”和“已发出但响应丢失” | 超时返回未知；客户端必须沿用原 ID 查询/重试，不能换 ID 重放 | 未知状态不被程序猜成成功或失败 |
| 参数冲突 | 旧票据路径通常产生另一份票据 | 同一 ID 改参数返回 `mobile_together_request_conflict` | 把客户端状态错误变成明确冲突 |
| token 安全 | 房间 URL 内含 Together 访问票据，旧链路需要保护整条 URL | 配对 token 与 session token 分离；手机响应不返回原始 `ticket_token`；URL 统一改写到 Reality 网关 | 减少内部票据暴露和端口暴露 |
| URL 与网络 | 旧路径可要求 Together 本地端口、固定公网 URL 或隧道 | `proxy_rooms=true` 时 `/join`、`/ws`、媒体和静态资源都经 Reality 转发；原生 Android 可 LAN 明文，浏览器通话仍要求 HTTPS | 手机只记一个网关地址 |
| V1 兼容 | 直接提供旧建房逻辑 | 仅当 V2 未匹配目标时回退；V2 匹配但未授权不回退 | 兼容不绕过授权 |
| 数据边界 | 依赖旧 Together 房间运行态 | V2 使用自己的身份和操作正本；不读取、迁移或修改 V1 用户数据 | 两代数据隔离 |

## 3. 已落地的组合优化

### 3.1 一个手机入口覆盖两个拓展

Reality 继续负责配对、移动会话、设备和网关代理；Together 继续负责房间、成员、实时连接和媒体；V2 负责身份、人格、权限和操作回执。手机不需要分别连接 Reality、Together 或 Screen，也不需要知道内部端口。

### 3.2 邀请和加入使用同一房间事实

房主邀请写入 Together 的 `InvitationStore`，受邀者按自己的 V2 scope 加入邀请指向的 `room_id`。同人重复加入是幂等重放，不新增成员；不同身份被接纳时提升 `member_revision`，在途输出可以按当前受众重新核验。

### 3.3 结果和凭据分开投影

V2 原生提供方保留完整操作账本和内部票据；Reality 手机 API 只投影 `room_id`、`invitation_id`、到期时间、模式和网关 URL。无论成功、失败还是未知，手机都拿不到 Together 原始 `ticket_token`、提示词原文或内部 scope 标识。

### 3.4 现实触及权限不随房间成员扩散

加入同一 Together 房间只改变该房间的文字、语音和插话受众。位置、摄像头、设备读取和设备控制仍按 Reality 的窗口授权、设备映射、白名单和当轮确认处理。受邀者不能因为拿到邀请就控制房主设备。

## 4. 当前仍需优化或现场确认

以下项目不应被本轮合成测试标记为完成：

- 当前仓库没有 Android 原生客户端源码；已完成的是服务端网关、API、URL 代理和 Together/V2 接线。真机配对、后台保活、系统权限、网络切换和电量策略仍需 Android 工程现场验证。
- 真实 HTTPS 反向代理、公网房间服务器、WebSocket、媒体流和浏览器摄像头/麦克风尚未现场验证。
- 真实 QQ 入站/出站、TTS/STT、米家设备和设备状态回读尚未现场验证；`confirmed` 只代表云端受理，不等于设备已经执行。
- V2 手机公开动作目前是建房、邀请和加入；成员列表、有效邀请列表和关闭房间仍通过原生 Together 工具与管理面使用，没有另造一组重复的手机端接口。
- V1 的旧 `resume`、旧客户端兼容别名和非 V2 目标仍保留，因此升级时应先观察 `/status` 的 `matched` 与 `capabilities`，再决定是否展示邀请/加入按钮。

## 5. 证据和验收口径

本轮源码证据包括：

- 本体 `tests.test_mobile_together`：6 项通过，覆盖 V2 逐动作授权、稳定请求 ID、未知结果约束、参数冲突、未匹配不重定向和多目标歧义。
- Reality 手机网关回归：此前 36 项通过，覆盖配对、状态、V2 优先建房、V2 授权失败不回退、邀请/加入 URL 改写和网关代理。
- `docs/REALITY_TOGETHER_V2_COMPOSITION_20261001.md`：记录同房成员连接、成员隔离、恢复和权限边界。

这些证据证明源码合同和合成网关路径，不证明真实 Android、QQ、设备、模型或公网链路已经可用。交付包构建和宿主验收以本轮构建输出目录及 `docs/BUILD_STATUS.md` 的最终记录为准。
