# ALIGN-01：多 Bot 作用域与角色归属首批切片

日期：2026-09-21。接续 [设计符合性检查](DESIGN_CONFORMANCE_AUDIT_20260921.md)。本轮把逻辑 Bot、登录账号、规范会话和 session 接入现有引用、持久记录、配置及对话链，并修复角色相册列表遗漏角色归属的问题。ALIGN-01 仍有绑定解析、运行实例上下文、旧归属映射和跨窗口资料投影工作，不能把本切片当作完整多 Bot 宿主支持。

后续进展：[人格解析与旧范围映射切片](ALIGN_PERSONA_RESOLUTION_AND_LEGACY_MAPPING_SLICE.md)已实现上述人格选择、运行上下文和映射登记原语；本文保留首批交付时的范围及测试证据。

## 1. 明确作用域与账号

[ScopeRef](../companion_v2/foundation/refs.py)保留原安装、平台、窗口类型、原生窗口 ID，新增四个独立字段：

| 字段 | 含义 |
| --- | --- |
| bot_id | 安装内的逻辑 Bot；不等于人格。 |
| account_id | 该平台的登录账号/连接身份；不等于消息发送者账号。 |
| conversation_id | 宿主已解析的规范会话身份；不把平台原生数字 ID 当全局会话键。 |
| session_id | 本次实际线程或会话实例；不得用最近活跃窗口猜测。 |

私聊、群聊和线程的四项路由字段必须一起提供；全部缺失仅表示旧格式未解析记录。安装级 SYSTEM 配置仍可合法不含用户、账号或 session，不伪造聊天上下文。

[AuthenticatedHostPrincipal](../companion_v2/identity_policy/models.py)另含 bot/login account 命名空间，原 `native_account_id` 继续表示真实发送者的外部账号。持久身份查询及唯一约束包含新命名空间；两个 Bot 收到同号用户不再落在同一默认绑定上。明确的可信身份关联仍可把多个平台账号映射到同一 Subject，不按名字或同号 ID 自动合并。

[窄宿主入站适配器](../companion_v2/adapters/astrbot/inbound.py)要求已解析作用域，并比对主体的 Bot/账号/平台。缺少路由返回 `scope_unresolved`，不匹配则失败；两种情况均不发布来源。当前适配器接收宿主提供的规范字段，尚未实现真实 AstrBot self_id/adapter/UMO 到这些字段的映射器。

## 2. 已接入的消费者

| 消费者 | 实际变化 |
| --- | --- |
| 身份、角色绑定及对象权限 | 精确查询、对象登记、可见列表和持久角色绑定包含全部新作用域字段。CORE 跨范围管理仍按显式目标与当前权限，不因命名空间隔离取消既有管理语义。 |
| 来源、资源和存储命名空间 | 保存及恢复完整 scope；新范围不能通过旧四字段相同就读取旧记录。来源/资产 ID 仍需提供方生成安装内唯一 ID，冲突返回错误。 |
| 对话、inbox/outbox | 原生事件号保留；来源、事件键、租约和新作用域下的操作身份纳入完整范围。同号事件在不同 Bot/账号/会话/session 下独立处理，同一范围重试仍恢复原操作。分段 ID 由其 operation 归属限定。 |
| 配置 | 角色层以安装+Bot+角色区分；窗口/SCOPE 目标保存完整作用域，窗口继承对应 Bot 的角色配置。安装级显式默认仍有意共享。旧未解析角色配置不会自动成为新 Bot 的角色配置。 |
| 便签和原操作 | 目标 JSON、稳定目标指纹、操作归属及重启恢复保留新增字段；不会用新的范围认领旧便签。完整个人资料跨窗口集合仍待进一步 owner/投影接入。 |
| 能力、家具与 Screen | 范围设置/授权包含新字段；角色启用加入逻辑 Bot，Screen 准入沿捕获来源的 Bot 读取对应角色选择。家具投影继续共用能力记录，不另存状态。 |

这次修改涉及共享 SQLite 结构和所有既有消费者，因此除新增测试外跑了一次全部隔离测试；后续小改继续只测受影响部分。

## 3. 角色归属与相册

新增 `RoleOwnerRef(installation_id, bot_id, persona_id)` 表示稳定的角色归属，不包含登录账号、窗口、session 或绑定 revision。现有 `SubjectKind.BOT` 的角色主体仍用于选择人格，逻辑 Bot 由作用域单独提供；两者不能互换。

[RoleLifeLedger](../companion_v2/role_work/models.py)现在从活动的可信 Bot/角色登记产物 owner。相册列表及单项读取必须指定 owner；同一窗口切换 A/B 不再混列产物，同一角色跨窗口或 session 可以查询自己的产物引用。传入与原活动不一致的 owner 会失败。角色活动仍为本地内存实现，尚未获得生活持久化和生命周期恢复证据。

[分享材料](../companion_v2/sharing/models.py)保留产物原 owner，[分享与追问](../companion_v2/sharing/planner.py)检查当前可信角色归属；B 不能把 A 的产物作为自己的相册材料续用。owner 清单是内部资料目录，不单独授予读取正文或面向用户分享的权利；原件仍检查来源权限、版本及受众。跨窗口的分享投影、其他角色材料的明确引用/转述尚待对应契约，不在此处隐式改写作者。

## 4. v5→v6 升级与旧归属

[数据库定义](../companion_v2/storage/schema.py)显式保留 v1-v5 DDL 和指纹，v6 对受影响表的路由字段、唯一约束及索引进行事务重建。旧列原值直接复制，不覆盖正文、owner、修订、撤回/共享状态、已领取提醒或未知外部结果。

旧记录的新字段以空存储值表示未解析，解码为 None，不映射成当前 Bot/账号。旧目标的 JSON 和指纹编码保持兼容；旧来源、身份绑定、角色配置和便签不会被新的完整作用域自动采用。本轮**没有执行旧数据归属重绑定**：需要后续提供带来源证据和版本的明确映射，处理旧混合/分叉记录及原操作结果，不能在升级时猜测。

SQLite 重建仅在初始化的未发布连接上暂时关闭外键执行；同一事务提交前做结构和引用检查，结束后恢复外键。失败回滚重建、版本及迁移记录。测试验证非空升级、重开不重复、建表后故障回滚、损坏引用、半升级、指纹变化、缺失索引和升级后外键约束。

这是 V2 内部格式升级，尚非 V1 用户数据迁移；没有接管任何生产数据根。大规模库升级耗时、真实备份/切换及并行旧 writer 交接仍待发行阶段取证。
