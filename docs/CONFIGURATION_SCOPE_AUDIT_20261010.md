# 配置作用域审计（2026-10-10）

审计结论：窗口被大量用作偏好的默认保存地址。需要整改的业务配置有 **15 个组，覆盖 405 个字段**；多目标模式还有 **20 个固定模型任务组、160 个字段**，以及 **7 个拓展偏好组、14 个字段**。图像和视频转述另有两个按模型能力注册的任务组，共 16 个字段。

这些数字表示存在作用域缺口的配置组及其覆盖字段。混合组中的权限、成员选择和隐私字段，需要与普通偏好分别处理。配置共享与聊天记录、记忆素材、授权、发送目的地的共享是独立问题。

本轮完成源码、API、页面和 V2 实际数据的审计，并保存逐字段清单。业务实现和线上配置的作用域尚未在本轮改动。

**结构问题与复现证据**

1. 公共编辑器只要看到组支持窗口，就默认选择窗口。

   `companion_v2/configuration/management.py:107` 的 `_target_layer()` 优先选择 `WINDOW`。因此记忆、知识库、群聊参与等已有安装和角色继承的组，在普通页面保存时仍会创建局部覆盖。该选择还决定窗口组的私聊对象校验，群相关控件通过私聊目标保存后，真实群读取时无法得到同一份值。

   专用回复、感知、表达和记忆编辑器也固定使用窗口目标。`astrbot_host/group_reply_api.py:104` 则固定创建当前群的完整窗口目标。

2. 部分共享只存在于 owner，注册表和管理合同仍为窗口。

   `ReplyConfigurationOwner` 只共享六个媒体场景开关。`PhysicalSettingsOwner` 共享 81 个状态字段，但这两组的字段工厂仍声明只有 `WINDOW`。`ConfigurationService._snapshot()` 在 `companion_v2/configuration/service.py:87` 按声明层拒绝其他目标，外部直接请求角色层会被拒。

   回复管理页又将六个字段的 `editable_layers` 改写成角色和窗口；保存目标继续是窗口。页面合同、注册合同和实际 owner 的地址因此不一致。

3. 旧窗口值可以压住角色值，保存还会顺带采用未修改的字段。

   `companion_v2/configuration/role_settings.py:27` 在角色值不强制覆盖时，只在窗口没有显式值的情况下采用角色值。QQ 空间全部 47 项都使用这一兼容分支。状态的身体、情绪和多数展示项，生活的睡眠项同样受影响。

   存储层合成复现：角色 `qzone.enabled=false`，旧窗口为 `true`，该窗口读取仍得到 `true`；角色 `role.state.hunger_enabled=false`，旧窗口为 `true`，该窗口也继续得到 `true`。

   同文件的 `write()` 会将角色尚未显式保存的共享字段，按当前窗口有效值整体采用。只修改一项也可能复制其他未修改的字段。后续应使用明确的稀疏修改和可追溯的兼容采用结果。

4. 已声明支持角色层的 owner，直接保存角色目标会版本冲突。

   `RoleSharedSettingsOwner.write()` 分别保存 role target 和原 target。原 target 本身就是 `ROLE` 时，两次写入落到同一个键；第一次递增版本后，第二次仍使用旧版本。外层事务随冲突回滚。

   合成复现：对技能组的角色目标保存 `custom_skills`，使用刚读取的版本，仍返回 `configuration_revision_conflict`。QQ 空间和生活使用相同基础写入逻辑。把页面目标简单改为角色，必须同时修复这条基础路径。

5. 模型任务默认按窗口保存；已保存的角色模型还会被宿主默认覆盖。

   `companion_v2/model_gateway/management.py:317` 读取窗口编辑快照，`:758` 固定写入窗口。每个任务的 provider、fallback、prompt、max_output_tokens、replacement_rules、fallback_on_refusal、timeout_seconds、replacement_scope 共八个字段都使用这个入口。

   `companion_v2/model_gateway/routing.py:70` 和 `:85` 用 `EffectiveValue.explicit` 判断模型是否已经配置。这个属性表示“由当前编辑层保存”。从角色或安装继承的已保存值，在窗口快照中仍为 `explicit=false`，随后会被 `provider_default()` 和 `apply_provider_default()` 的宿主默认覆盖。

   合成复现：角色层已保存 `provider=role-model`，窗口正确读到来源 `role`，应用宿主默认后实际路由变为 `host-model`。收敛作用域时必须同时修正来源判断。

6. 同一用户或群更换 conversation 后会换配置地址。

   `ConfigTarget.document()` 将完整 `ScopeRef.document()` 纳入窗口键。完整 scope 包含 `account_id`、`conversation_id` 和 `session_id`。因此同一 Bot、角色、群和 session 更换 conversation ID，就会产生新的窗口配置键。

   合成复现：旧群窗口主唤醒开关为 `false`；只替换 conversation ID 后，新目标读取回默认 `true`。持久的角色、用户偏好及逐群例外应使用稳定身份地址。

7. 工作台通过继承链误判“角色共享”；同组单一层合同促成了隐藏共享。

   `pages/陪伴小屋/workbench-page.js:725` 只要 `layers_of(target)` 包含角色层，就显示“角色共享 · 本会话可覆盖”。每个普通窗口的 chain 本来就包含安装和角色，这一标签不能证明组会读取或保存角色值。

   同时，`FieldRegistry` 要求一个组所有字段具有完全相同的 `layers`。状态、生活等组混合了角色偏好和窗口授权，只能通过 owner 偷换字段层。需要为偏好和授权提供各自明确的合同，页面按真实写入范围显示。

   共享 owner 还将角色快照中的 `explicit=true` 直接复制到窗口快照。合成复现：窗口未保存 QQ 空间开关，值来自 `role`，却报告 `explicit=true`。该标志应该表达当前编辑层是否拥有值，否则修改与恢复继承的提示会继续误导用户。

8. 七项拓展偏好只有 exact scope，没有安装或角色继承。

   `companion_v2/capabilities/configuration.py` 为每个拓展注册 `proactive_enabled`、`thought_weight`，声明层均为 `SCOPE`。`ConfigTarget.chain()` 对 `SCOPE` 只返回自身。偏好记录保存在 `capability_settings`，与普通配置值分开。

   这两个偏好需要安装或角色默认，以及明确的局部选择。能力授权本身已经由独立 consent 记录管理，继续保留原始授权边界。尤其 `thought_weight` 属于行为偏好，不能因换窗口或设备会话而丢失默认值。

当前角色的稳定地址为安装、Bot 和角色，去除 account、conversation 和 session；跨 Bot 共用的默认值放安装层。私聊与群聊的概率、能力开关和默认策略仍可分别配置，配置的保存范围从窗口转为角色。

修正工作需覆盖字段声明、owner、管理 API、运行消费者、旧记录兼容和唯一小屋页面。先修共享 owner 的角色写入和模型继承，再把偏好与授权合同分开，最后统一页面默认保存范围及范围说明。旧窗口记录保留证据，区分历史公共保存、用户明确例外和临时测试设置；有冲突的私人内容保持原归属。单项保存采用稀疏修改，继续保留版本校验、操作回执和未知结果确认。

后续实现完成一个板块后做最小定向检查，全部作用域接线完成后从当时源码构建新包并统一验收。验收应覆盖跨窗口、换 conversation、角色隔离、安装默认与显式角色值、局部例外、关闭开关、恢复继承、旧值冲突、授权保持，以及新解包的宿主加载、停机和路由注销。

**本轮验证和复现方式**
