# 已保存运行档的工具目录装配修复

日期：2026-10-11。

## 根因

七项内置能力声明 63 个工具：Content 7、Image 3、Screen 1、Reality 8、Together 7、Game 35、Live 2。QQ 空间提供另外 4 个工具。宿主装配时，`CompositeAstrBotToolPort` 将合并后的 67 个注册工具与单次插件模型请求的 `MAX_TOOL_CATALOG = 64` 比较，抛出 `composed host tool catalog exceeds its bound`。

异常发生在 `load_existing → _assemble → MultiHostSession → AstrBotCompanionHost`，因此角色运行环境没有完成装配，页面只能显示配置加载失败和数据不可读取。此次失败发生在注册阶段，与角色是否启用这些工具、当前用户是否有调用权限无关。

外部原生能力发现也曾因聚合工具超过 64 个而清空整份目录；单个原生声明同样误用了该模型请求数量限制。

## 修复

安装级工具注册、原生声明解析和宿主工具合并均保留完整的可信目录，不再依赖单次插件模型请求的数量限制。原生声明仍验证 UTF-8 JSON 字节预算、完整字段、唯一动作和真实包身份；重复工具身份、动作归属冲突、卸载和原权限检查仍按原合同处理。

单次插件模型请求继续由模型网关与 wire 验证其目录预算。普通对话工具由 AstrBot 主链按已认证事件和当前授权注入，调用结果仍由原工具所有者提供，不经过插件回复模型计费。

本次修复不更改运行档、角色映射、能力授权或配置存储结构。

## 实际运行中发现的可选日历故障

本地重载日志确认 2.1.0 已加载原运行档并接收入站。随后 Windows 记录宿主 Python 原生崩溃：`python312.dll / c0000005`；该记录不足以确定原生崩溃的完整调用链。通过原有 `launch_backend.py` 恢复后台并为此次恢复启用 Python faulthandler，输出保存在交付目录。

冷启动成功后，实际宿主的可选农历包文件不可读取，`PermissionError` 从 `lunar_date_parts` 传到宿主调度器，导致 `host_dispatch_failed`。日历组件现将可选库导入及其文件读取的 `OSError` 按既有缺失库合同处理：尝试备用农历库，均不可用时明确投影 `lunar_status=unavailable`，仍保留真实公历日期、时区、时间与周期。可选节假日库也按既有星期回退规则处理文件读取失败。未知农历不补造；原身份、授权和其他关键组件的异常不由该处理捕获。

## 回归范围

- 单个声明和聚合目录超过 64 个时保留全部工具，过大 JSON、空声明和重复动作仍拒绝。
- 原生工具与 QQ 空间合并后，末尾工具仍路由到原端口；卸载后不能继续调用。
- 实际七模块与 QQ 空间组成的宿主连续两次冷启动，核对保存的运行档、工具目录、开始接收入站、停机和路由注销。
- 超过 64 个工具的主链请求能够执行末尾工具，使用原身份和真实执行回执，且不创建插件回复模型调用。
- 可选农历与节假日库的导入、文件读取失败不会中断公历投影；备用农历库可用时使用其实际结果。
- 从本次源码新构建交付包后，在隔离的 AstrBot 自带运行环境验证宿主入口、生命周期和相关工具合同；结果与包哈希保存在交付目录。
