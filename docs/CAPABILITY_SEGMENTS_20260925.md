# 陪伴能力分段框架（修正版）

日期：2026-09-25
适用范围：`astrbot_plugin_private_companion_v2`（V2）功能盘点、与 V1 差距重排、进度看板分段

---

## 一、为什么不用「六层信息流」切法

初版按信息流向切了六层（感知 → 理解 → 自我 → 决策 → 行动 → 表达）。这个模型失效的原因不是分得不够细，而是**切错了维度**：

陪伴系统里有一批功能天生是**通道 / 触点**，同时具备入站与出站两半。戳一戳、图片、语音、撤回、表情回应都是如此。任何线性分层都会把它们切碎，或者被迫塞进某一层而丢掉另一半的信息。

更麻烦的是，同一个触点的两半进度往往不同步。戳一戳就是典型：入站的事件通路已经能收，出站的回戳与主动戳一行代码都没有。归到「感知」会掩盖出站缺口，归到「表达」会掩盖入站已通的事实。

所以框架改成**分段（segment）+ 跨段落位**：先定义几段互不重叠的能力区间，再允许单个功能占据多段。

## 二、四段主干 + 一条横切

| 段 | 职责 | 判据 |
|---|---|---|
| **环境接入** | 从外部世界获得素材 | 产物是给角色内部使用的新信息 |
| **角色内核** | 认知（关于用户）、自我（关于角色）、决策（做什么） | 不产生对外输出的内部运转 |
| **产出** | 内容从无到有 | 产生用户可见的新产物，或改变外部状态 |
| **投递** | 内容已经存在，决定怎么送出去 | 不创造新内容，只决定形态、顺序、时机、通道 |
| **治理（横切）** | 身份授权、来源治理、撤回传播、隐私隔离、预算、诊断恢复 | 不产生面向用户的功能，但约束以上每一段 |

### 环境接入的两个子类

这一段的重点不在「收到用户消息」，而在**外部素材源**，可再分：

1. **环境源**：天气与预警、新闻与搜索、时间与农历节日、外部系统数据。
2. **交互源与媒体增强**：入站图片理解、动画抽帧、音频入站、引用、转发、撤回通知、入站戳一戳、群事件。

第二类中的「媒体增强」（例如把入站图片转成更好的文字描述、动画抽帧后供模型查看）容易被误判为表达。判据是**产物的消费者**：产物喂给角色内部认知，就是环境接入；产物给用户看，才是产出或投递。

### 产出与投递的划界判据

这是最容易糊在一起的两段，用一条可操作的判据分开：

- **产出** = 内容从无到有。画一张图、写一篇日记、打一局游戏、调整设备。
- **投递** = 内容已存在，决定怎么送。是否分段、是否转语音、是否附原图、是否插入表情、是否先显示「正在输入」。

一个完整功能常常**先产出、后投递**。归类时看它主要在哪一端创造价值：生图归产出，附原图回发归投递。

## 三、跨段功能落位（V2 实测）

按源码实际接线判定，非按测试数量。

| 功能 | 环境接入 | 角色内核 | 产出 | 投递 |
|---|---|---|---|---|
| **戳一戳** | 事件通路已在 notice 入口收得到（仅通路，无专属业务） | — | — | 回戳、主动戳：**完全缺失** |
| **图片** | 入站理解与动画抽帧（`conversation/media/`） | — | 生成已通基础链；入站编辑与蒙版**缺** | 附原图（`media/reply.py`）、表情图库（`expression/reactions.py`）已通 |
| **语音** | 入站音频（`media/audio/service.py`） | — | — | TTS 合成**缺**；仅有模型标注的 spoken 片段与呈现策略，无合成 |
| **撤回** | 撤回通知已通（22 项，现场待验） | — | — | 主动撤回己方消息、撤回回看**未迁入** |
| **表情** | — | — | — | 图库检索与投递已通，复用 `delivery/media` |
| **天气** | 外部数据源**完全缺失**（核心包零命中） | — | — | — |

### 关于 P06 的口径修正

差距审计原文把「戳一戳与普通 QQ 状态」标为**部分完成**，理由是输入提示与自定义短状态已接入。这个说法掩盖了分段的另一半，建议改成：

> **部分完成，且两半不同步。** 投递侧：正在输入与自定义短状态已由 `adapters/astrbot/presence.py` 实现（`platform.typing`、`platform.presence`），归属 `delivery/`。环境接入侧：戳一戳事件在 notice 入口可被接收，但无任何专属业务处理。投递侧的回戳、主动戳，以及在线/离开/忙碌/隐身切换，**完全缺失**。

代码证据：`companion_v2` 生产代码中 `poke` 零命中，仅出现在 docs 与 `tests/recall_entry_process.py`（把 `notice_type=notify, sub_type=poke` 当作入站事件，断言它不被当作撤回处理）。

## 四、各段对应的 V2 目录

| 段 | 目录 |
|---|---|
| 环境接入 | `conversation/media/`（图片、音频、视频、动画）、`quotes/`、`forwards/`、`astrbot_host/recalls.py` |
| 角色内核 | `memory/`（含 `group/slang.py`）、`relationships/`、`identity_policy/personas`、`role_work/state/`、`role_work/growth/`、`agenda/planning.py`、`proactive/`、`conversation/participation.py` |
| 产出 | `role_work/life/`、`role_work/journal/writing`、`conversation/content/`、Image 与 Content 伴侣原生链 |
| 投递 | `conversation/generation.py`、`segmentation.py`、`voice_reply.py`、`delivery/`（含 `presence.py`、`media.py`）、`expression/reactions.py`、`adapters/astrbot/onebot.py` |
| 治理 | `identity_policy/`、`sources/governance.py`、`configuration/`、`model_gateway/`、`diagnostics/`、`storage/` |

注意 `delivery/presence.py` 与 `adapters/astrbot/presence.py` 同属投递段——**代码本身就把平台动作类输出放在投递域**，这正是分段框架的依据来源之一。

## 五、按段重排后的差距形状

- **环境接入**：V2 最薄的一段。交互源（撤回、引用、转发、群事件、媒体）基本齐，环境源（天气、新闻、搜索）一片空白。群黑话学习已接通，气氛维护、昵称校正、群事件整理仍缺。
- **角色内核**：V2 与 V1 大致持平，局部更强（群黑话学习、关系提案跨会话延续）。
- **产出**：V2 最弱。只有阅读/睡眠/日记/梦境加 Image、Content 两条基础链；七个伴侣里五个在这段是空的。
- **投递**：中等偏上。分段、流式、图片、表情、QQ 平台动作都在；缺 TTS、合并转发输出、跨会话转述、撤回己方消息。
- **治理**：V2 明显强于 V1，是重写的核心收益。

一句话：**V2 的力气花在内核与治理，V1 的厚度压在产出与投递；而环境接入是两边都欠的账。**
