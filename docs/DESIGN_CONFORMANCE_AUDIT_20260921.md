日期：2026-09-21。范围：独立 V2 源码、既有测试、V1 仓库中的现行设计及功能清单。结论：当前实现符合部分局部设计，尚未具备完整多 Bot/多人格运行和统一答疑能力；不能从已有便签、配置或 Screen 测试推断这些横向要求已经完成。

本次用合成数据复现并修复了已实现对话链的隔离、角色版本和资料使用问题。完整作用域、领域归属、权限统一与诊断服务仍需先补，后续顺序按本文第 5 节执行。

## 3. 已复现并修复的对话问题

| 问题 | 修复前证据 | 本轮修复 |
| --- | --- | --- |
| 私聊与群聊复用租约 | 同安装、同原生窗口 ID 和事件号，PRIVATE/GROUP 两事件拿到相同 lease；第二份 lease 仍指向第一份 source。 | 增加事件的规范化 scope 键；租约包含当前 ScopeRef 的全部维度。取消一份不取消另一份。 |
| 同号消息跨窗口冲突 | A/B 两窗口具有相同原生事件号、不同内容，第二条返回 `inbox_event_conflict`。 | G3/G4 inbox 使用 scope 化事件标识，保留原事件号用于归因；同窗口重试仍识别为同一事件。 |
| 人格切换后旧草稿继续提交 | 本地模型在生成中把窗口由 A 绑定到 B，旧 A 草稿仍成功创建 1 条 outbox。 | 前台要求原 `RoleBinding`，生成前、生成后和提交前重验；便签工具从原 PromptRequest 取绑定，不在新建工具会话时重新给旧提示词盖上当前绑定。 |
| 旧角色操作被新角色解释为自身回执 | 原前台操作参数仅记录输入内容指纹。 | 本地操作参数另含原角色/绑定 revision 指纹；角色改变后不能重放为同一角色操作。旧回执不被重写，完整历史说话者记录仍待 CORE-02。 |
| 资料先交给模型，最后才检查 | 原 G4 在模型生成后才逐项读取 contribution 的来源，不能保证模型输入已获当前授权。 | 在生成前、修订前及提交前复核资料。全部已声明受众都须在资料授权受众内；便签续答同样检查原上下文材料。无来源的内部投影仍需后续 owner/Actor 契约。 |
| 用消息到达时间代替当前检查时间 | 原 G4 的授权/资料过期复核及全部阶段时间均使用 `event.received_at`。 | 注入当前时钟，检查生成期间到期和真实阶段时间；事件收到时间仍保留。没有据此声称已测得真实回复延迟。 |

主要代码：[事件标识](../companion_v2/conversation/models.py)、[G3 链](../companion_v2/conversation/kernel.py)、[前台链](../companion_v2/conversation/foreground.py)、[便签工具](../companion_v2/conversation/agenda_tools.py)、[绑定契约](../companion_v2/identity_policy/models.py)。

修复仅覆盖当前四字段 ScopeRef 能表达的空间，不构成多 Bot 验收。没有把 bot、账号或 session 拼进 `native_scope_id` 假装完成新契约，也没有给旧资料补一个猜测的默认 Bot。

数据库结构仍为 v5。现有操作标识未改写，新增 scope 化 inbox 键不自动重解释旧无范围 inbox。旧 G4 本地操作不具备角色指纹时，不能当作新契约下可重放的角色结果；新链会出现参数冲突，旧记录保留。它们从未获得外部发送资格，后续任务/迁移接入时必须明确整理，不能直接接 sender。提交前复核仍不等于已具备跨 worker 的执行租约或 Delivery fencing。

## 4. 答疑必须按原设计补齐

[入口台账](../companion_v2/legacy/surface_ledger.py)现已分别登记“查看主动判定”“答疑/诊断/说明”“答疑确认”“答疑取消”和“答疑设置”，台账条目不表示路由已实现。

| 模式或入口 | 首批实际责任 |
| --- | --- |
| explain | 根据功能定义、配置含义及设计解释，不声称检查过运行状态。 |
| self_check | 读取指定 Bot/角色/范围的配置、采用回执、能力和任务状态；检查未运行或证据不足时为 unknown。 |
| incident | 根据具体范围、时间窗和原 trace/operation 重建故障；区分未开始、排队、取消、失败、未知和已确认效果。 |
| repair_proposal | 保存可核对的字段差异、依据、影响范围、角色和原版本；诊断本身不修改配置或设备。 |
| 确认/取消/显式设置 | 绑定原建议和真实操作者；确认时重验当前权限、范围、角色及 revision，再调用公共配置服务。取消不应用建议；显式管理设置仍经过同一权限与版本规则。 |

检查描述需带版本、范围、权限、成本、超时、时效及无副作用声明；结果采用 pass/warn/fail/unknown/not_applicable，带实际时间与脱敏证据。L0/L1 按需读取，L2 限定故障时间窗，L3 仅在对应授权下探测。缓存键包含作用域、配置/策略修订及数据版本；答疑不新增全量扫描、永久轮询或每轮固定模型检查。

用户答复沿原角色按需要组织信息，语义由模型理解；技术检查提供真实材料。无需向用户朗读统一五段模板，也不能把说明书检索结果写成“刚刚已检查”。

## 5. 调整后的前置顺序与验收

下列是既有设计的实施补齐，不改变产品路线。原“直接进入 CORE-08/02”的下一步细化为先过三个前置切片，再接真实任务消费者；可以继续隔离实现，但不能跳过它们宣布宿主就绪。

1. **ALIGN-01：完整作用域与稳定归属。** 先补可信 RuntimeScope、逻辑 Bot/登录账号/会话/线程与角色快照；确定各领域稳定 owner 和版本化编码。同步接身份授权、来源投影、配置目标、能力选择与角色生活。v5 非空资料通过有证据的映射升级；不能确认的范围明确未解析，保留原件，不按当前 Bot/主人格认领。
2. **ALIGN-02：公共权限覆盖实际消费者。** 将配置和能力管理逐动作接到安装身份政策，保留字段/对象范围和明确开放语义；核心全权不能只在便签成立，重要用户也不能因此自动获得核心管理或他人私密资料权限。完成可信管理入口与领域服务之间的调用合同。
3. **ALIGN-03：最小真实诊断与答疑材料。** 建立 Check/Result/Report 与有范围的查询，先读已有配置采用、能力、存储和操作结果；确认/取消建议复用公共配置服务。暂缺的 worker/provider 状态返回 unknown，随 CORE-08 接入实际证据。
4. **继续 CORE-08/CORE-02。** 有界任务、模型/提示词来源、预算/用量、取消与恢复、事件合并、逐段回执和真实已发历史；携带前三步的 scope、角色和诊断关联。前台不串行等待无关后台维护，真实输出另按 G8 验收。
