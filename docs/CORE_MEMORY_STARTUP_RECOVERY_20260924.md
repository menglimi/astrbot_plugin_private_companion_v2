# V2 记忆启动后自动接续

本切片接续[模型输出容错](CORE_MEMORY_OUTPUT_RECOVERY_20260924.md)和[恢复队列](CORE_MEMORY_RECOVERY_QUEUE_20260924.md)。原实现已经能通过显式调用恢复保存点，但宿主重启不会主动执行这些方法；每日任务又会在执行前把 next_at 推到次日，导致已经收到的模型结果继续等待。

现在，统一宿主完成任务与投递账本的恢复后，会在现有唤醒循环中启动一次有界的记忆检查。不增加 SQL 表、schema 迁移、模型调用或独立后台 worker。

## 实际行为

| 中断位置 | 启动后的处理 |
| --- | --- |
| received：已保存脱敏模型原返回，尚未解析 | 读取原返回，重新解析、校验并保存有效项 |
| modelled：已校验，尚未全部写入 | 复用逐项回执，继续剩余项，保留已写入项的原编号和回执 |
| 子修复已经完整保存，父批次尚未回填 | 按原关联回填父批次状态与回执 |
| 每日整理已保存，但 pending_batch / covered_until 尚未收尾 | 复用正常日程的收尾方法；有剩余来源时仍安排后续窗口，有延后材料时不虚报覆盖 |
| prepared：仅完成准备 | 保留原状态，不把“准备好了”当作执行授权 |
| running：调用结果待核对 | 保留未知结果，不重放模型请求；原日程窗口可解除挂起，让后续新材料继续处理 |
| 已保存的原返回仍有格式问题 | 保留失败或部分保存记录，进入既有管理修复队列；启动恢复不会另外请求模型修格式 |

恢复成功不发送消息，管理接口继续复用现有状态与逐项回执，不返回 raw_output。正常执行中的一次自动格式修复仍沿用已有配置；本次启动扫描只处理本地保存步骤。

## 有界扫描与生命周期

- 启动时在一致读快照中记录 memory_reflections 和 memory_schedules 的行号上界；先处理记忆保存点，再收尾日程。
- 每次唤醒最多检查 8 条持久记录，按 rowid 继续前进。失败或无权处理的记录不会反复占住第一页。空表直接跳过，扫描结束后不再查询恢复队列。
- 游标属于本次宿主生命周期；再次重启可以从头检查，持久状态和原操作回执保证幂等。上界之后的新工作由原执行链负责，本切片不增加常驻全表轮询。
- 记忆启动扫描完成前，正常每日整理暂缓派发，避免日程绕过恢复边界抢先处理原批次。前台对话及其他领域仍使用原宿主循环。
- 恢复直接在现有驱动器内执行。每批之间让出事件循环；停机取消原驱动器并停止扫描，不产生脱离生命周期的 worker。
- 自动恢复时，当前宿主代际核对与本地保存共用写事务，其他进程接管后旧宿主不能再提交。原来的逐项回执仍保留；自动恢复中的新步骤作为该保存点的一次本地事务提交，失败时回滚到此前的持久保存点。

`MemorySchedule.recovery.report` 提供本次扫描状态、检查数、处理数及受阻原因计数，供可信宿主诊断使用。计数对象包含记忆记录和日程收尾，不能把 recovered 当作新增事实数量；没有另加管理 API。

## 授权与并发边界

恢复继续调用原记忆服务，重新核对当前账号绑定、角色、会话、受众、记忆权限、来源、配置令牌、日程版本和事实版本。关闭记忆、撤销身份、撤回来源或暂停日程都不能通过重启绕过。需要重新准备的旧结果保留原返回和失败原因；没有丢弃用户数据。

有持久返回不表示旧 worker 已停止。凡记录了 task_id 的保存点，原任务必须进入终态，且所有尝试都已释放实际运行名额，才可继续本地处理；检查也接入显式 `MemoryReflection.run()`，防止正常日程或管理恢复与仍在运行的旧 worker 竞争。没有 task_id 的旧本地保存点保留兼容。

受阻记录本次不会自动轮询重试。用户处理权限或旧 worker 状态后，可以使用既有管理恢复入口，或在下次启动时重新核对。未知调用和新模型修复仍使用已有独立边界。
