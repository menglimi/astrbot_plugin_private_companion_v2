# 原生 QQ 撤回通知与来源失效

日期：2026-09-25。本片把 OneBot `friend_recall` / `group_recall` 通知接到 V2 现有来源治理和会话执行链，补齐此前只有领域撤回接口、没有原生事件入口的缺口。

## 事件与原消息

`main.py` 独立注册 notice 观察入口，普通会话 handler 排除 notice。撤回通知不产生对话、不触发模型，也不会阻止其他插件观察该通知。

`astrbot_host/recalls.py` 核对原 SDK 事件类型、当前连接账号、已配置私聊或群目标，以及原平台实例、client、消息与会话字段。群管理员的 `operator_id` 是操作者，原消息作者仍取 `user_id`。真实 SDK 为 notice 自身分配新 UUID，因此撤回的消息号只取 `raw_message.message_id`，兼容有效的负数消息号。

`conversation/recalls.py` 使用 installation、platform、bot、account、private/group、原生会话地址、消息号和原作者共同定位原件。不会用当前人格或重置后的 conversation/session 重算旧消息身份。私群、账号和 Bot 即使出现同号消息也不互相撤回。

## 持久事实与消费

撤回标记复用 `inbox`，消费者为 `conversation.platform_recall.v1`，没有新增 schema。即使原件尚未入库也保存标记；后到原件、引用和确认回复的物化都复核它。重复通知只返回原事实，重启后也不会使原件恢复。

一次事务内完成标记、入站 withdrawn、原 Source 撤销、已封存批次失效以及未发送分段取消。尚未封存的合并批次可继续使用剩余有效输入；已经用过撤回材料的旧生成不能改用另一份材料继续发送。

原件撤回沿既有 Source 依赖传播到引用、媒体、记忆和已确认 Bot 回复来源。历史读取、群历史、提醒或主动投递历史，以及确认回复来源物化都复核可定位的原平台消息。Bot 自身消息被撤回时保留原平台 ACK 和实际送达记录，只停止正文与图片的后续使用，不把已发送改成未发送，也不补发。

源材料在捕获、生成或分段投递期间失效时，后续步骤沿现有执行检查中止。外部效果或投递结果未知仍保留原 unknown 屏障；撤回不是重放未知操作的许可。

## 验证

- `tests/test_platform_recalls.py`：4 项，覆盖合并批次剩余原文、派生来源与重启、作者/账号/peer/Bot 隔离、Bot 回执保留及零补发。
- `tests/test_astrbot_recall_host.py` 与独立 SDK 子进程：18 个独立用例通过，覆盖私群、多账号、管理员代撤回、先撤后入、原会话/人格变化、连接替换、捕获/生成/首段发送在途、引用失效、unknown ACK 重启，以及入口启停和路由注销。详细证据见[宿主测试记录](RECALL_HOST_TEST_REPORT_20260925.md)。
- 撤回、引用、群引用、后台历史、宿主、恢复与隔离共 74 项回归：首轮 73 项通过，满 32 条输入与两个串行后继的旧用例因单个 3 秒等待预算不足超时；独立复跑通过，剖析确认三个 flow 完成、模型 3 次、发送 6 次。仅该用例等待预算调整为 10 秒，连同默认等待路径复验 2 项通过，行为断言保持原值。

测试使用 AstrBot 自带 Python，SDK 数据根指向临时目录；模型、OneBot 和人物均为合成夹具。真实 SDK `convert_message → create_event → main.py` 已通过，未以此代替现场 QQ/模型验收。没有读取 V1 用户数据、在线重载或更新原发行 ZIP。

## 边界与下一步

本片接收平台已发生的撤回事实，不新增 `delete_msg` 主动撤回工具，也不恢复查询已撤回正文的旧功能。实际平台是否上报某类撤回仍由适配器和服务端决定。

下一步在新的集成快照中做单账号现场验收，检查真实通知、引用失效与后续消息行为；本体后续开发继续补生活计划、真实活动来源和多来源主动联系。
